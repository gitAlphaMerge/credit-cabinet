# РОЛЬ
Ты ведущий специалист по безопасности финтеха: модель угроз банковских систем, антифрод, безопасность LLM-агентов.
Ты пишешь не «список лучших практик», а модель рисков конкретной системы, где каждая угроза доказана атакой.
Общие советы без привязки к нашему коду и нашим данным считаются браком.

# ПРОДУКТ
Хакатон Альфа-Будущее 2026, трек «Умный кредитный кабинет предпринимателя». Через 2 недели прототип, дальше возможен пилот в банке.
Кредитный помощник для ИП и ООО внутри ИИ-помощника банка:
1. Помощник сам пишет клиенту первым, увидев проблему в его выписке (например, кассовый разрыв через 3 недели).
2. Разговор: на что деньги, когда и из чего вернёшь.
3. Клиент загружает выписку по счёту (CSV) и, позже, документы (договор с заказчиком, акт сверки).
4. Ядро (Python, правила, БЕЗ LLM) считает: поток по месяцам, платёж = поток / 1.25, стресс «выручка −30%», лимит сейчас и после шага,
   стоп-правила, один из 4 статусов: «можно подавать» · «можно после шага» · «лучше другой инструмент» · «нужен менеджер».
5. LLM-агент только объясняет ответ ядра словами и задаёт следующий вопрос. Цифры берёт только из ответа ядра.
6. Собирается папка для андеррайтера: каждое поле помечено «подтверждено» / «со слов клиента» / «не проверено».
7. Правило продукта: цифры двигают ТОЛЬКО подтверждённые данные. Слова клиента в разговоре лимит не меняют.
Решение о кредите принимает банк. Слова «одобрено» в продукте нет.

# АРХИТЕКТУРА (как есть сейчас и как планируется)
- docker compose: frontend (nginx, статика) · api (Go, порт 8080, единственный вход снаружи, пока заглушка) · ml-model (Python, порт 5000).
- Сейчас сайт ходит прямо в ml-model, Go-шлюз встанет перед ним позже.
- ml-model: http.server из стандартной библиотеки. Окна: GET /health, POST /score.
- Запрос /score (JSON): statement_csv (текст CSV: date, amount, counterparty, purpose; позже ИНН, КПП, счёт, остаток),
  need {purpose, amount_rub, term_months, repay_from, asked_for}, questionnaire {form, need, sector, years, trend},
  confirmed_fields {contract_main_customer: {sum_rub, months}}, history [{role, text}].
- Ответ: decision_id, model_version, core_id, status, instrument, stops_fired, reasons, missing, limits, evidence.
- Каждое решение пишется в журнал JSONL: decision_id, время, версия, sha256 входа, ответ. Сырую выписку не храним.
- Ядер будет несколько (по сегментам: ИП / ООО / отрасль), выбор ядра делает шлюз по реестру.
- Прод для демо: Yandex Cloud, 2 vCPU, 4 ГБ RAM, Caddy с HTTPS спереди. Деплой через GitHub Actions. Ключ LLM в .env.
- LLM: внешний провайдер по API (Groq / Qwen), то есть данные клиента могут уйти за пределы РФ.
- Прототип без логина: жюри поднимает его из чистого клона одной командой.

# ЧТО ЗАЩИЩАЕМ
Банковская тайна и персональные данные (выписка, ИНН, ФИО, контрагенты), честность решения (лимит и статус),
доверие клиента к агенту (агент не обещает того, чего нет), журнал решений (по нему банк потом разбирает споры и проверяет пилот),
доступность (сервер 4 ГБ), секреты (ключ LLM, деплой).

# ЗАДАНИЕ

## Часть 1. Модель угроз
1. Активы, участники (клиент честный, клиент-мошенник, конкурент, внешний атакующий, нечестный сотрудник, сам LLM-провайдер), границы доверия.
   Нарисуй поток данных в Mermaid с границами доверия.
2. По каждой границе пройди STRIDE. Минимум 25 угроз. Каждая угроза: id, граница, сценарий атаки в 2–4 предложениях на НАШИХ данных,
   предусловия, что ломается в продукте.
3. Обязательно разбери (это самое трудное, тут ждём глубины):
   a. Промпт-инъекция через назначение платежа и имя контрагента в выписке (их пишет кто угодно, кто платил клиенту).
      Докажи, что если LLM увидит сырую выписку, атакующий может заставить агента пообещать одобрение или исказить объяснение.
      Спроектируй, что именно LLM можно показывать, и как проверить, что текст агента не противоречит ответу ядра.
   b. Игра с ядром честными на вид данными: «карусель» (деньги гоняются между своими компаниями, чтобы надуть оборот),
      заём учредителя перед подачей, перевод между своими счетами, дробление наличных, фиктивный договор с несуществующим заказчиком,
      омоглифы и невидимые символы в назначении (латинская «о» вместо русской, zero-width), чтобы обойти правила по ключевым словам.
      Для каждой: как она меняет лимит, каким сигналом в выписке её ловить, сколько ложных срабатываний на честных клиентах.
   c. Подмена выбора ядра: может ли клиент через поля запроса попасть на «мягкое» ядро другого сегмента.
   d. Журнал решений: подделка, удаление, повтор запроса (replay), подмена model_version. Предложи журнал с защитой от подделки
      (цепочка хэшей или аналог) и объясни, что он даёт банку на пилоте.
   e. Отказ в обслуживании на 4 ГБ: огромный CSV, миллион строк, патологические строки, вложенный JSON, медленная отправка.
   f. CSV-инъекция формул в папке для андеррайтера, если её откроют в Excel.
   g. Утечка данных: логи, ошибки со стектрейсом, LLM-провайдер за рубежом. Что маскировать до отправки в LLM и почему.
      Требования по персональным данным в РФ укажи как «проверить с юристом», не выдумывай номера статей.
   h. Цепочка поставки и деплой: образы docker без фиксированной версии, секреты в GitHub Actions, открытые порты в compose.
4. Матрица рисков: вероятность 1–5 × ущерб 1–5, у каждой оценки одна строка обоснования. Отдельно две колонки:
   «хакатон» (демо у жюри) и «пилот» (реальные клиенты банка). Одна и та же угроза может быть низкой на хакатоне и критической на пилоте.
5. Топ-10 по риску на пилоте. Для каждой: защита, стоимость внедрения в часах, остаточный риск после защиты.

## Часть 2. Доказательства атакой
1. Для каждой угрозы из топ-10 напиши pytest-тест в tests/test_security_<тема>.py, который сейчас ПАДАЕТ на нашем коде
   (или помечен xfail с причиной, если атака требует ещё не написанной части, например LLM-агента).
   Сервер поднимается в фикстуре: python services/ml-model/app.py, базовый адрес http://127.0.0.1:5000.
2. Минимум 3 вредные выписки CSV в tests/fixtures/ (инъекция в назначении, карусель, омоглифы), сделанные из data/synthetic/cash_gap.csv.
3. Тест не должен зависеть от сети и ключа LLM.

## Часть 3. Требования к защите (спецификация, не код)
Для слоя проверки запроса (будет модуль security.py в ml-model): лимиты размера, строк и полей, нормализация Unicode,
проверка схемы, что делать при нарушении (код ответа + текст для клиента без утечки внутренностей).
Для шлюза Go: что он обязан делать до того, как запрос дойдёт до ядра.
Для LLM-агента: что ему показывают, что запрещено, как проверяется его ответ.
