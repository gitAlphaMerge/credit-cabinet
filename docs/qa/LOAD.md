# F4: нагрузка и память, 23.10.2026

## Результат и граница вывода

На Windows Node 24.16.0 отдельный API-процесс после исправления документов
проходит 750 путей за три круга, но с настройками V8 по умолчанию достигает
278,42 MiB RSS. Цель 220 MiB без настройки запуска не выполнена.
С `--max-old-space-size=64` тот же процесс и те же 750 путей проходят с пиком
200,12 MiB. Это проверенное предложение владельцу запуска, а не изменение
Docker-конфигурации. `mem_limit: 256m` не изменён. Docker/cgroup не проверялись.

## Как измерялось

Seed 2302, три круга по 200 последовательных и 50 одновременных клиентов.
Реальные регистрация/scrypt, cookie, lookup/confirm, PATCH анкеты, upload/confirm,
подбор, создание заявки, submit. На каждом пути проверяются offered и ровно один
make_offer. Ядро заменено одинаковым детерминированным ответом, LLM выключена.
Тестовый loopback proxy разрешён только в обвязке, лимиты приложения сохранены.

Исходная обвязка держит генератор, supertest, приложение и SQLite `:memory:`
в одном процессе. Изолированный режим запускает приложение в дочернем процессе
с теми же статическими middleware и `listen`, что в production-ветке index.ts.
Генератор живёт отдельно, его RSS не входит в метрику сервера. SQLite использует
пустое имя файла: это дисковая временная БД SQLite, автоматически закрываемая
самой SQLite. Она не эквивалентна постоянной WAL-БД контейнера.
Доступ к событиям для изолированного режима проверяется через настоящий GET
деталей заявки: submit не возвращает весь журнал. Этот дополнительный GET входит
в обе сравниваемые изолированные серии до/после.

Dockerfile вызывает `npm start`, package.json запускает `tsx server/index.ts`.
`npm run build` выполняет `tsc --noEmit && vite build`, отдельного скомпилированного
сервера здесь нет. В песочнице tsx падает до приложения:
`uv_os_get_passwd ENOMEM`. Поэтому использован существующий native Node QA-loader
с transform TypeScript. В изолированном аналоге нет dotenv, автозапуска агента
и Vite; статическая сборка не создавалась за пределами разрешённых файлов.
Это аналог production API, не заявление об успешном старте Docker/npm start.

RSS выбирается каждые 10 мс, в исходной обвязке также после каждого шага.
`Q2_MEMORY` выводит rss, heapTotal, heapUsed, external, arrayBuffers перед
нагрузкой и после последовательной/параллельной части каждого круга.
Пик внутри блокирующего scrypt может быть пропущен. Один прогон не доказывает
отсутствие утечки, накопление данных в SQLite ожидаемо. Параллельно шли другие
проверки, задержки не являются SLA.

## Профиль кучи и исправленный источник затрат

`v8.getHeapSnapshot()` вызывается после последней параллельной фазы, рядом с
наблюдаемым пиком. Снимок разбирается в памяти, сырые строки и файл со снимком
не сохраняются. Он вызывает GC и сам требует память, поэтому отдельные
диагностические серии нельзя использовать для RSS-приёмки.

До фикса, изолированный сервер, круг 3: строки 20766112 байт,
code 9405232, массивы 4789416, JSArrayBufferData 3494879,
object shape 2174048, Object 674824, Module 130288 (1003 объекта).
Перед snapshot: rss 311525376, heapUsed 90051904 байт.

После фикса, изолированный сервер, отдельный диагностический круг 1:
строки 13708696 байт, code 7490192, массивы 3593808,
JSArrayBufferData 3458399, object shape 1586128, Object 465264.
Перед snapshot: rss 188637184, heapUsed 38768376 байт.
Непосредственные сильные ссылки на строки/массивы: code 13688832 байт,
synthetic roots 9301096, array 2357784, Object 1765624, Module 1208416.
Это суммы shallow size по ссылкам, общие объекты могут считаться несколько раз;
это не dominator retained size. Серии имеют разное число кругов, поэтому
разность размеров не является точной оценкой освобождённой памяти.
Нативные выделения SQLite/scrypt в этих размерах V8 не видны.

Доказанный лишний расход в разрешённом участке: каждый CSV создавал полную
ExcelJS Workbook, копию строк и текстовую копию таблицы; при старте CSV-сервера
безусловно загружались также PDF/DOCX/XLSX-библиотеки. CSV теперь разбирается
напрямую с кавычками/переносами, текстовая копия для табличной выписки не
строится, тяжёлые библиотеки загружаются только для своего расширения.
Стартовый RSS изолированного сервера снизился с 155230208 до 109907968 байт.
Предел размера финансовых записей не ослаблен: 8 MiB файла, 50000 операций
плюс заголовок; прежний предел извлечённого нетабличного текста сохранён.

## Повторить

Команды PowerShell из `hw/tolya/alfa-intellect/`, без сети и установки пакетов.
Каждую серию запускать с указанными переменными и без остальных `Q2_*` overrides.

Исходный режим:

```powershell
node --import ./scripts/qa/q2-runtime.ts scripts/qa/q2-load.ts
```

Изолированный режим с исходными настройками памяти:

```powershell
$env:Q2_MODE='production'
node --import ./scripts/qa/q2-runtime.ts scripts/qa/q2-load.ts
```

Проверенное предложение по heap, три круга по умолчанию:

```powershell
$env:Q2_MODE='production'
$env:Q2_HEAP_MB='64'
node --import ./scripts/qa/q2-runtime.ts scripts/qa/q2-load.ts
```

Диагностика после фикса:

```powershell
$env:Q2_MODE='production'
$env:Q2_ROUNDS='1'
$env:Q2_SNAPSHOT='round-1:parallel'
node --import ./scripts/qa/q2-runtime.ts scripts/qa/q2-load.ts
```

Для исходных документов установить `Q2_BASELINE_DOCUMENTS='1'`: QA-loader
читает `git show HEAD:hw/tolya/alfa-intellect/server/documents.ts`, не меняя
рабочие файлы. После включения фикса в HEAD исходной версией это уже не будет.
Для диагностической серии до фикса использовались три круга и
`Q2_SNAPSHOT='round-3:parallel'`.

В изолированном режиме без snapshot скрипт возвращает exit 1 и при ошибках
сценария, и при RSS больше 220 MiB. Изменение heap не применяется молча:
`Q2_HEAP_MB` влияет только на дочерний измеряемый сервер.

## Нужно от владельца запуска

Проверить `NODE_OPTIONS=--max-old-space-size=64` в реальном Docker с постоянной
WAL-БД и текущим `mem_limit: 256m`, включая загрузку PDF/XLSX/DOCX после прогрева.
Если подтвердится, применить настройку запуска в принадлежащем ему файле.
Этот фикс F4 сам по себе не гарантирует лимит контейнера. RSS после третьего
круга с флагом всё ещё растёт; более длинная серия не проверялась.
