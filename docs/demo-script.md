# Демо жюри без LLM: Q5

Состояние на 23.10: S1 и S4 проходят серверные проверки. S-менеджер заблокирован воспроизводимым дефектом: после полного client_update заявка автоматически становится offered вместо возврата в queued. Шаги ниже совпадают с q5-jury-path.test.ts; последний сценарий намеренно красный. Не объявлять его пройденным и не менять статус SQL-запросом.

## Подготовка

Нужны уже установленные зависимости кабинета, Node 24 и Python со стандартной библиотекой. Для живого показа нужен запущенный локальный API с ядром Лизы: TEAM_API_URL указывает на него, CORE_ID=liza задаётся процессу ml-model. В корневом docker-compose.yml это уже установлено. Проверки реестров синтетические, EGR_PROVIDER=mock. Сеть, установка пакетов и запуск Docker в этой QA-сессии не выполнялись.

Из hw/tolya/alfa-intellect в PowerShell, при уже работающем локальном API:

```powershell
$env:AI_PROVIDER = ''
$env:TEAM_AGENT_URL = ''
$env:EGR_PROVIDER = 'mock'
$env:TEAM_API_URL = 'http://127.0.0.1:8080'
.\node_modules\.bin\tsx.cmd scripts/seed-manager.ts
```

DATABASE_PATH должен совпадать у сида и кабинета. Если переменная не задана, оба используют var/alfa.sqlite относительно рабочей папки. При запуске кабинета в контейнере сид также запускать в его контейнере с тем же томом, например из корня репозитория:

```text
docker compose exec -e AI_PROVIDER= -e TEAM_AGENT_URL= -e EGR_PROVIDER=mock alfa-intellect npx --no-install tsx scripts/seed-manager.ts
```

Для отключения LLM в живом кабинете пустые AI_PROVIDER и TEAM_AGENT_URL должны быть заданы именно процессу сервера, не только команде сида. Корневой compose задаёт TEAM_AGENT_URL непустым, поэтому его стандартный запуск сам по себе не подтверждает режим без LLM.

Сид создаёт менеджера 79990000500 и клиентов 79990000501..79990000504. Случайные пароли выводятся только при первом создании в консоль, в файлы сид их не записывает. Повторный запуск не меняет пароли и работу менеджера, не создаёт новые заявки. Если пароль потерян, повторный запуск его не восстановит. При недоступности ядра команда завершается с ошибкой, оставляет draft без досье; после восстановления её можно повторить.

Открыть кабинет http://127.0.0.1:4173 и войти менеджером с напечатанным паролем. На новой базе во вкладке «Очередь» ровно четыре заявки:

| Телефон | Кейс | Причина |
|---|---|---|
| 79990000501 | ООО, мебель | Договор и акт основного покупателя не подтверждены; напоминание, молчание |
| 79990000502 | ИП, пекарня | Сумма выше лимита, клиент не согласен с альтернативами |
| 79990000503 | ООО, текстиль | Выписка короче 12 месяцев; напоминание, молчание |
| 79990000504 | ИП, ремонт | N=4 из M=5, не заполнен возраст бизнеса; напоминание, молчание |

Порядок вычисляет сервер: min(сумма, лимит) * (N/M) / (1 + число дыр) + 20000 * часы ожидания при стандартной PRIORITY_AGING_K. При изменении настройки коэффициент берётся из неё. Не сортировать вручную.

## S1: зелёная заявка

1. Тест создаёт отдельного синтетического клиента 79990000511: действующее ИП пекарни, полная анкета, диверсифицированная выписка за 12 месяцев и текущий месяц. Запрос 300000 рублей на 12 месяцев, «Кассовый разрыв».
2. Клиент создаёт заявку через createApplication и отправляет submit с consent=true через executeApplicationEvent.
3. Результат offered. Журнал: create, submit, underwriter_approve, make_offer. Последние три события от system, менеджера нет.
4. Оффер содержит 12 платежей, сумма основной части 300000 рублей. Заявки нет в очереди менеджера.

## S4: комплаенс-стоп

1. Тест создаёт отдельного клиента 79990000514 с существующим локальным ИНН 9900000002, у которого реестр показывает LIQUIDATED. Это старый мок с некорректной контрольной цифрой, он не входит в новые Q5-компании.
2. Клиент создаёт заявку и отправляет submit с consent=true.
3. Результат rejected, причина COMPLIANCE_EGRUL_INACTIVE, клиентский текст сообщает о недействующем бизнесе. Ядро не вызывалось. Заявки нет в очереди.

## S-менеджер: ожидаемый сценарий, сейчас BUG

1. Сид формирует очередь, менеджер выбирает 79990000501 с отсутствующими договором и актом.
2. Менеджер отправляет request_info с hole=contract_main_customer и текстом «Дослать договор и акт сверки». Статус info_requested.
3. Клиент отправляет client_update с confirmed_fields: contract_main_customer и reconciliation_act, оба документа подтверждены.
4. Ожидается queued, затем менеджер отправляет send_to_underwriting с memo «Документы проверены, передать андеррайтеру.». Ожидается offered и записка в журнале.

Фактически шаг 3 сразу даёт offered. Тест останавливается на assert queued, шаг 4 не выполняется. Если оставить досье неполным, отправка андеррайтеру запрещена. Требуется решение владельца P2 о возврате заявки после ручного дозапроса; Q5 не меняет контракт и чужой серверный код.

## Повторить проверки

Из hw/tolya/alfa-intellect:

```text
npx --no-install tsc --noEmit
npx --no-install tsx --test tests/qa/q5-seed.test.ts
npx --no-install tsx --test tests/qa/q5-jury-path.test.ts
```

Если tsx падает с uv_os_get_passwd ENOMEM, доступен запуск без tsx:

```text
node --experimental-transform-types tests/qa/q5-run.ts ./q5-seed.test.ts
node --experimental-transform-types tests/qa/q5-run.ts ./q5-jury-path.test.ts
```

Эти тесты не открывают сетевые соединения: перехватывают только fetch-транспорт httpCoreClient, запускают настоящий cores.REGISTRY['liza'] адаптер через Python. Сериализация клиента, скоринг, комплаенс, БКИ, машина состояний и SQLite настоящие; транспорт API, HTTP-маршруты, браузер и app.decide/guards не проверяются. AI_PROVIDER и TEAM_AGENT_URL явно пустые. Для входов тестов нет случайного seed, все бизнес-данные фиксированы, часы 2026-10-23T12:00:00Z. Случайны лишь UUID и секреты, они не влияют на ожидаемые исходы.
