# Демо жюри без LLM: Q5

Состояние на 23.10: S1, S4 и все ветки S-менеджер проверяются тестами. Решение 23.10: после досылки выполняется повторный скоринг. Зелёный результат получает автоматический оффер, если менеджер не поставил галочку «Вернуть мне после досылки». Красный результат возвращает заявку менеджеру с исходной причиной. Статусы вручную через SQL не меняются.

## Подготовка

Для Compose Node на хосте не нужен: зависимости, tsx и скрипты находятся в образе кабинета. Для отдельного локального запуска нужны установленные зависимости кабинета, Node 24 и Python со стандартной библиотекой. Для живого показа нужен запущенный локальный API с ядром Лизы: TEAM_API_URL указывает на него, CORE_ID=liza задаётся процессу ml-model. В корневом docker-compose.yml это уже установлено. Проверки реестров синтетические, EGR_PROVIDER=mock.

Из hw/tolya/alfa-intellect в PowerShell, при уже работающем локальном API:

```powershell
$env:AI_PROVIDER = ''
$env:TEAM_AGENT_URL = ''
$env:EGR_PROVIDER = 'mock'
$env:TEAM_API_URL = 'http://127.0.0.1:8080'
.\node_modules\.bin\tsx.cmd scripts/seed-manager.ts
```

DATABASE_PATH должен совпадать у сида и кабинета. Если переменная не задана, оба используют var/alfa.sqlite относительно рабочей папки. При запуске кабинета в контейнере сид также запускать в его контейнере с тем же томом, например из корня репозитория:

```text
docker compose exec -T -e AI_PROVIDER= -e TEAM_AGENT_URL= -e EGR_PROVIDER=mock alfa-intellect npx --no-install tsx scripts/seed-manager.ts
```

В корневом Compose кабинет обращается к командному агенту через TEAM_AGENT_URL. По умолчанию AGENT_LLM_URL пустой, поэтому агент отвечает без модели и запросов к LLM. Пустые AI_PROVIDER и TEAM_AGENT_URL в команде выше относятся к процессу сида; они не меняют конфигурацию уже работающего сервера.

Сид создаёт менеджера 79990000500 и клиентов 79990000501..79990000504. Случайные пароли выводятся только при первом создании в консоль, в файлы сид их не записывает. Повторный запуск не меняет пароли и работу менеджера, не создаёт новые заявки. Если пароль потерян, повторный запуск его не восстановит. При недоступности ядра команда завершается с ошибкой, оставляет draft без досье; после восстановления её можно повторить.

Открыть кабинет http://127.0.0.1:4173 и войти менеджером с напечатанным паролем. На новой базе во вкладке «Очередь» ровно четыре заявки:

| Телефон | Кейс | Причина |
|---|---|---|
| 79990000501 | ООО, мебель | Договор и акт основного покупателя не подтверждены; напоминание, молчание |
| 79990000502 | ИП, пекарня | Сумма выше лимита, клиент не согласен с альтернативами |
| 79990000503 | ООО, текстиль | Выписка короче 12 месяцев; напоминание, молчание |
| 79990000504 | ИП, ремонт | N=4 из M=5, не заполнен возраст бизнеса; напоминание, молчание |

Порядок вычисляет сервер: min(сумма, лимит) * (N/M) / (1 + число дыр) + 20000 * часы ожидания при стандартной PRIORITY_AGING_K. При изменении настройки коэффициент берётся из неё. Не сортировать вручную.

## Оффер, подпись и демонстрационная выдача

В рабочем месте менеджера у заявки 79990000502 выберите альтернативу в пределах лимита, заполните записку и нажмите «Предложить вариант». В открывшейся записке отметьте «Я проверил досье и согласен с запиской» и нажмите «Передать андеррайтеру». Передача на андеррайтинг запускает переходы underwriting → approved → offered. Войдите клиентом 79990000502 с паролем из сида: оффер показывает график платежей. Нажмите «Подписать договор» и введите код 0000. Сервер фиксирует signed, затем автоматически disbursed с сообщением «Деньги на счёте». SMS и реального перевода денег нет. Менеджер может отказать заявке в очереди с указанием причины, клиент видит причину отказа.

Для досылки через интерфейс используйте заявку 79990000503 с короткой выпиской: менеджер запрашивает недостающую выписку, клиент загружает и подтверждает финансовый документ в «Моей заявке», выбирает его и нажимает «Дослать». Итог зависит от повторного скоринга. Загрузчик не принимает договоры и акты из API-ветки ниже.

## S1: зелёная заявка

1. Тест создаёт отдельного синтетического клиента 79990000511: действующее ИП пекарни, полная анкета, диверсифицированная выписка за 12 месяцев и текущий месяц. Запрос 300000 рублей на 12 месяцев, «Кассовый разрыв».
2. Клиент создаёт заявку через createApplication и отправляет submit с consent=true через executeApplicationEvent.
3. Результат offered. Журнал: create, submit, underwriter_approve, make_offer. Последние три события от system, менеджера нет.
4. Оффер содержит 12 платежей, сумма основной части 300000 рублей. Заявки нет в очереди менеджера.

## S4: комплаенс-стоп

1. Тест создаёт отдельного клиента 79990000514 с существующим локальным ИНН 9900000002, у которого реестр показывает LIQUIDATED. Это старый мок с некорректной контрольной цифрой, он не входит в новые Q5-компании.
2. Клиент создаёт заявку и отправляет submit с consent=true.
3. Результат rejected, причина COMPLIANCE_EGRUL_INACTIVE, клиентский текст сообщает о недействующем бизнесе. Ядро не вызывалось. Заявки нет в очереди.

## S-менеджер: зелёный результат после досылки

1. Сид формирует очередь, менеджер выбирает 79990000501 с отсутствующими договором и актом.
2. Менеджер отправляет request_info с hole=contract_main_customer и текстом «Дослать договор и акт сверки». Статус info_requested.
3. Клиент отправляет client_update с confirmed_fields: contract_main_customer и reconciliation_act, оба документа подтверждены.
4. Результат offered автоматически. Журнал заканчивается client_update, underwriter_approve, make_offer от system. Заявки нет в очереди, записка менеджера не нужна.

Вторая ветка: клиент 79990000502 уже отказался уменьшать сумму. Менеджер запрашивает выписку, клиент досылает её. Скоринг повторяется, сумма остаётся выше лимита. Заявка сразу возвращается в очередь с CLIENT_DISAGREED и исходными тезисами клиента. Повтор HTTP-запроса с тем же Idempotency-Key не добавляет событий.

Третья ветка, галочка «Вернуть мне после досылки». Менеджер ставит её рядом с «Запросить документ» (request_info с return_to_manager=true). Клиент досылает документ, скоринг повторяется. Даже при зелёном результате заявка возвращается в очередь с бейджем «вы просили вернуть», рядом новый вердикт ядра. Без галочки зелёная заявка уходит клиенту сама. Следующий запрос документа без галочки флаг снимает.

## F1: клиентская подача и очередь без сида

Открыть «Финансирование», выбрать условия и нажать «Отправить заявление». Текст перед кнопкой фиксирует согласие на обработку данных и запрос БКИ в демонстрации. POST /api/selections/:id/application с consent=true вызывает createApplication и submit машины состояний, сохраняет старую запись funding_applications и контактный лид. Ответ содержит applicationId и applicationStatus. При сбое проверок возвращается понятная ошибка, лид успеха не создаётся; повтор продолжает тот же draft.

Чат подбора получает принадлежащую клиенту активную заявку, N/M, дыры, лимит и альтернативы. Реплика «Не согласен с альтернативами» приводит к системному escalate_disagreed даже при выключенной LLM. Для явного отказа через API: POST /api/applications/:id/disagreement с expectedVersion и client_objections. Подмена X-Role не меняет роль из сессии. Прямые системные события через /events возвращают 403.

Числовой порог молчания в контракте не найден. Конфиг демонстрации: APPLICATION_SILENCE_MS, по умолчанию 86400000 (сутки после напоминания); APPLICATION_SWEEP_MS, по умолчанию 60000 (обход раз в минуту). Оба значения целые положительные, в миллисекундах. Переменные задаются процессу сервера до запуска. Обход сначала пишет agent_nudge и доставляет сообщение в чат подбора, затем после порога без ответа вызывает escalate_silent с actorRole=system и причиной CLIENT_SILENT. Ответ клиента отменяет эту эскалацию. Таймер не удерживает процесс и не перекрывает собственный предыдущий обход.

Ручной обход против той же локальной БД, без создания сидовых клиентов:

```powershell
.\node_modules\.bin\tsx.cmd scripts/seed-manager.ts --sweep-silent
```

Первый вызов доставляет напоминание, повтор после APPLICATION_SILENCE_MS ставит молчащую заявку в очередь. Ручной вызов не обходит порог и не выдаёт клиенту системные полномочия.

Ограничение стыка: возврат всё ещё красной заявки после прежнего CLIENT_SILENT и ручного дозапроса требует отдельного перехода машины состояний. Текущее API позволяет CLIENT_SILENT только после нового напоминания; немедленная повторная эскалация ложно назвала бы ответившего клиента молчащим. F1 этого не делает, описывает зависимость владельцу F2 в REPORT.md.

## Повторить проверки

### G2: переключение готовых демонстрационных профилей

Подготовка G2 пока требует добавления молодой синтетической компании `9900050032` в моки ЕГРЮЛ и проверок. До этого полный сид останавливается с ошибкой и не заменяет существующие данные. См. корневой REPORT.md.

После добавления моков задайте `DEMO_PERSONAS=1` процессу сервера и сида. По умолчанию режим выключен: GET /api/demo-personas и POST /api/demo-personas/switch возвращают 404, демонстрационных профилей в меню нет. Логины и пароли в меню не показываются. Внешние сервисы и LLM для подготовки не нужны; нужен локальный API с ядром Лизы (`TEAM_API_URL`, `CORE_ID=liza`).

Из hw/tolya/alfa-intellect в PowerShell, с уже установленными зависимостями:

```powershell
$env:DEMO_PERSONAS = '1'
$env:AI_PROVIDER = ''
$env:TEAM_AGENT_URL = ''
$env:TEAM_API_URL = 'http://127.0.0.1:8080'
.\node_modules\.bin\tsx.cmd scripts/seed-demo.ts
```

В контейнере нужны пять видимых выписок. Для этого владелец compose должен подключить `./data/v3:/app/demo-data/v3:ro` и задать `DEMO_DATA_ROOT=/app/demo-data` только процессу сида или сервису. По умолчанию локальный сид читает data/v3 из корня репозитория. Этот том пока не добавлен, docker-compose.yml в G2 не менялся.

DATABASE_PATH у сида и сервера должен совпадать. Обычный повтор сохраняет те же учётные записи, заявки, пароли и работу менеджера. Для возврата всех шести персон в начало предусмотрен явный CLI-флаг:

```powershell
.\node_modules\.bin\tsx.cmd scripts/seed-demo.ts --reset
```

Если установленный tsx падает с uv_os_get_passwd ENOMEM, без установки пакетов доступен тот же сид через штатный QA-загрузчик: `node --import ./tests/qa/q3-loader.ts scripts/seed-demo.ts --reset`.

CLI выбран вместо кнопки, чтобы жюри случайно не сбросило ход демонстрации. Сначала все пять заявок пересчитываются на настоящем ядре в отдельной SQLite, затем новые данные атомарно заменяют только данные этих демо-пользователей. Сбой ядра сохраняет прежнее демо. При явном сбросе идентификаторы заявок меняются, идентификаторы пользователей и пароли сохраняются. Чужие учётные записи не меняются.

Войдите обычным способом или откройте существующий вход в демонстрационный кабинет. Нажмите значок профиля справа в шапке. В меню есть переход в профиль компании и шесть сценариев, текущий отмечен текстом и галочкой. Выбор клиента сразу открывает «Моя заявка», выбор менеджера открывает его рабочее место. Полная навигация после смены серверной сессии очищает память предыдущего экрана. Без режима демо меню содержит только обычный переход в профиль.

| Профиль | Что показывает | Ожидаемый статус |
|---|---|---|
| Пекарня «Колос» | 3 млн рублей, полные данные, автоматический оффер | offered |
| Сервис техники | 800 тыс. рублей, лимит ниже запроса, альтернативы | info_requested |
| Мебель на заказ | 300 тыс. рублей, менеджер запросил договор и акт, «Вернуть мне после досылки» включено | info_requested |
| Молодая мастерская | 200 тыс. рублей, история бизнеса короче года | rejected, TOO_YOUNG, видна менеджеру в отказах |
| Ткани и пошив | 400 тыс. рублей, короткая выписка, напоминание и молчание | queued, CLIENT_SILENT |
| Менеджер банка | Очередь, запрос документов и отказы | роль manager, собственной заявки нет |

Статус молодого бизнеса следует замороженному контракту: жёсткий стоп ядра означает rejected с видимостью менеджеру, а не произвольный перевод в queued. Все операции берутся из пяти разных видимых выписок data/v3. Календарь сдвигается целыми месяцами к последнему завершённому месяцу, суммы и состав операций сохраняются. Лимиты и свободный поток рассчитываются ядром, в данных персон их нет. Подготовка завершится с ошибкой при несовпадении ожидаемой ветки, отсутствии альтернатив или отсутствии TOO_YOUNG у молодой персоны.

Проверка G2 с настоящим локальным HTTP и ядром Лизы, без подмены fetch и результата скоринга:

```text
node --import ./tests/qa/q3-loader.ts --test tests/qa/g2-personas.test.ts tests/qa/g2-menu.test.tsx
```

Временный локальный /score в тесте использует производственный cores.REGISTRY['liza']; клиентские и банковские запросы проходят Express через supertest и настоящие cookie-сессии. Переключение принимает только ключ из списка персон, проверяет серверный is_demo и роль. Передать ID, телефон или роль обычного пользователя этим маршрутом нельзя.

Из hw/tolya/alfa-intellect:

```text
npx --no-install tsc --noEmit
npx --no-install tsx --test tests/qa/q5-seed.test.ts
npx --no-install tsx --test tests/qa/q5-jury-path.test.ts
npx --no-install tsx --test tests/qa/f1-path.test.ts
```

Если tsx падает с uv_os_get_passwd ENOMEM, доступен запуск без tsx:

```text
node --experimental-transform-types tests/qa/q5-run.ts ./q5-seed.test.ts
node --experimental-transform-types tests/qa/q5-run.ts ./q5-jury-path.test.ts
```

Q5 перехватывает fetch-транспорт httpCoreClient и запускает настоящий cores.REGISTRY['liza'] адаптер через Python. Сериализация, скоринг, комплаенс, БКИ, машина состояний и SQLite настоящие. Файлы q5-seed и q5-jury-path запускать отдельными процессами: каждый рассчитывает на свою пустую SQLite. F1 использует настоящий локальный HTTP через supertest, Express и SQLite; внешние проверки и ядро заменены детерминированными адаптерами. Это проверка проводов, не качества скоринга. Браузер, Docker и реальные внешние сервисы этими тестами не проверяются. AI_PROVIDER и TEAM_AGENT_URL явно пустые.
