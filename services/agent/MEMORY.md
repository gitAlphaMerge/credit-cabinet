# MEMORY.md: как агент помнит клиента

Решение архитектора 20.10. Код пишется под этот файл, не наоборот.

## Три слоя

```
слой          что лежит                                  где                                      живёт
рабочая       последние 8 реплик дословно                state["history"] в сессии                 разговор
сессия        слоты need, view, попытки, trace           sessions/<sha256(session_id)>.json        разговор, переживает рестарт
клиент        факты о клиенте и бизнесе (≤ 30 штук)      clients/<sha256(client_id)>.json          между разговорами
```

`client_id` передаёт сайт в `/turn` (у Толи: id пользователя). Нет `client_id`, нет третьего слоя: разговор помнится, клиент нет.

## Факт

```json
{"id": "f7", "text": "продаёт плитку, главный заказчик платит на 60-й день", "kind": "business",
 "source_turn": 4, "created_at": "...", "updated_at": "...", "status": "active",
 "history": [{"text": "главный заказчик платит на 45-й день", "until": "..."}]}
```

`kind`: `business` (чем занимается, сезонность, заказчики), `need` (что хотел, на что деньги), `preference` (как удобнее общаться: коротко, голосом, вечером), `progress` (что обещал прислать, что уже прислал, чем закончился расчёт: статус словами, без чисел).

## Автообновление (после каждого хода)

Схема Mem0 (Chhikara et al., 2025), упрощённая под ≤ 30 фактов, без векторной базы: все факты клиента целиком лежат в промпте.

1. **Извлечь.** LLM получает последнюю пару «клиент → агент» и текущие факты, возвращает JSON-операции:
   `ADD {text, kind}` · `UPDATE {id, text}` (уточнил или поправил) · `DELETE {id}` (сам опроверг: «уже не надо») · `NOOP`.
2. **Проверить кодом.** Операция отбрасывается, если в тексте: ИНН, паспорт, телефон, карта, email, ФИО третьих лиц, суммы из `view`, содержимое выписки. Факт ≤ 200 символов. Неизвестный `id` у UPDATE/DELETE = отброс.
3. **Применить.** UPDATE и DELETE не стирают: старый текст уходит в `history` с `until`, DELETE ставит `status: "deleted"`. Так видно, что клиент передумал, и ничего не теряется безвозвратно.
4. **Ужать.** Больше 30 активных фактов: самые старые `progress` уходят в `status: "archived"`.
5. **Записать** атомарно (tmp + rename), как сессии.

Обновление не должно тормозить ответ: сначала ответ клиенту, потом память (в том же потоке после отправки, либо фоновым потоком с блокировкой на `client_id`). Ошибка обновления пишется в лог, на ответ не влияет.

Без ключа LLM работает урезанный режим правилами: заполненные слоты `purpose`, `amount_rub` клиента, `repay_from` и статус расчёта словами пишутся как факты `need` и `progress`.

## Как память идёт в ответ

В системный промпт реплики добавляется блок «Что вы знаете о клиенте» (активные факты, новые сверху) и «Последние реплики». Первая реплика нового разговора при непустой памяти опирается на неё: «В прошлый раз говорили про закупку плитки под объект. Это ещё в силе?»

## Чего память не хранит

Выписку и её строки, ИНН, паспорт, телефон, карты, пароли, имена контрагентов из выписки, числа ядра. Клиент попросил «забудь меня» → все факты `status: "deleted"`, файл переписан без `text` и `history`.
